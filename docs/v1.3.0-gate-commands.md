# 1.3.0 gate commands

Exact commands for the parts of the 1.3.0 install/verification gate that
aren't just "open a page and look." Written against the release
candidate at commit `7c6635697817584c68721ecfe83fe54d4024059d`, artifact
SHA-256 `19BC1D93091537EABD9548C1B4F26C103ADAC2B53BC59959907118D1696FFD82`.

Assumes: BBS installed from that exact MSI, default install (service
running, listening on `127.0.0.1:8000`). All commands are Windows
PowerShell 5.1. Replace `$SqlHost` / `$SqlInstance` / `$Database` in
section 2 with your real values if they differ from the placeholders
shown.

**If any `Invoke-RestMethod` call below fails with a non-2xx status,
PowerShell throws instead of returning the response body.** Read the
actual error with:

```powershell
$_.ErrorDetails.Message
```

## 2. Throwaway login: create, verify, drop

**Read this before running anything in this section.**

- Verifying a login through BBS -- real or throwaway -- always saves it
  as BBS's active SQL configuration and takes effect immediately, no
  restart needed. From the moment step 2.2's verify succeeds until you
  finish step 2.5, BBS is reading RaceManager as `bbs_connector_test`,
  not `bbs_connector`. That's harmless while the test login still
  exists (it has the same read-only access), but BBS **will start
  failing to reach RaceManager the instant you drop it in step 2.4**,
  and stays failing until step 2.5 finishes. Do this between events.
- BBS never returns a saved SQL password back to you -- `/configuration`
  and `GET /api/configuration` always show it blank. Step 2.5 restores
  BBS by generating a **new** password for the real `bbs_connector`, not
  by recalling the old one. There's nothing to write down first.
- You need `sqlcmd` available for step 2.4 (cleanup is never run
  automatically, by design). If you don't have it: `winget install
  Microsoft.SQLServerCmdLineUtils`, or paste the SQL into SSMS instead
  of using `-i`.

Set your real values first:

```powershell
$SqlHost = "localhost"     # your RaceManager SQL Server host
$SqlInstance = "USABMX"    # your SQL Server instance name
$Database = "RACE"
```

If you're connecting to a **default (unnamed) instance**, set
`$SqlInstance = ""` and use `sqlcmd -S $SqlHost` (no trailing backslash)
in place of `sqlcmd -S "$SqlHost\$SqlInstance"` wherever it appears
below.

### 2.1 Generate the create plan

```powershell
$plan = Invoke-RestMethod -Uri "http://127.0.0.1:8000/api/setup/sql/plan" -Method Post -ContentType "application/json" -Body (@{
    host = $SqlHost; instance = $SqlInstance; database = $Database; login_name = "bbs_connector_test"
} | ConvertTo-Json)
$plan.kind
$plan.sql
```

**Pass looks like:** `$plan.kind` is `create` (not `reset_password` --
`bbs_connector_test` shouldn't exist yet), and `$plan.sql` contains
`CREATE LOGIN [bbs_connector_test]`.

**If this throws a 409** ("Could not connect with Windows
authentication..."), BBS's own connection can't reach this SQL Server
with enough privilege from here -- expected if BBS and this SQL Server
are on different computers. Skip to 2.1-offline below instead of 2.2.

#### 2.1-offline (only if 2.1 threw a 409)

```powershell
$offline = Invoke-RestMethod -Uri "http://127.0.0.1:8000/api/setup/sql/generate" -Method Post -ContentType "application/json" -Body (@{
    database = $Database; login_name = "bbs_connector_test"
} | ConvertTo-Json)
$offline.sql | Out-File -FilePath "$env:TEMP\bbs-test-login-create.sql" -Encoding utf8
sqlcmd -S "$SqlHost\$SqlInstance" -E -i "$env:TEMP\bbs-test-login-create.sql"
```

**Pass looks like:** `sqlcmd` exits with no error text. Then skip to 2.3
(you already created it yourself, so there's nothing to "run" -- only
verify).

### 2.2 Run it and verify (only if 2.1 succeeded, not 2.1-offline)

```powershell
$apply = Invoke-RestMethod -Uri "http://127.0.0.1:8000/api/setup/sql/apply" -Method Post -ContentType "application/json" -Body (@{
    plan_id = $plan.plan_id; host = $SqlHost; instance = $SqlInstance; database = $Database
} | ConvertTo-Json)
$apply.verified
$apply.proof
```

**Pass looks like:** `$apply.verified` is `True`, `$apply.proof.login` is
`bbs_connector_test`, `$apply.proof.row_found` is `True`.

If you went through 2.1-offline instead, verify with the password from
`$offline.sql` (copy it out of that generated script) instead of
`$apply`:

```powershell
$offlinePassword = "PASTE-THE-PASSWORD-FROM-offline.sql-HERE"
$verify = Invoke-RestMethod -Uri "http://127.0.0.1:8000/api/setup/sql/verify-and-store" -Method Post -ContentType "application/json" -Body (@{
    host = $SqlHost; instance = $SqlInstance; database = $Database
    login_name = "bbs_connector_test"; password = $offlinePassword
} | ConvertTo-Json)
$verify.verified
```

**Pass looks like:** `$verify.verified` is `True`.

### 2.3 Confirm it's live

```powershell
(Invoke-RestMethod http://127.0.0.1:8000/api/configuration).sql_user
```

**Pass looks like:** outputs `bbs_connector_test`.

### 2.4 Drop it

```powershell
$cleanup = Invoke-RestMethod -Uri "http://127.0.0.1:8000/api/setup/sql/cleanup?database=$Database&login_name=bbs_connector_test" -Method Get
$cleanup.sql | Out-File -FilePath "$env:TEMP\bbs-test-login-cleanup.sql" -Encoding utf8
sqlcmd -S "$SqlHost\$SqlInstance" -E -i "$env:TEMP\bbs-test-login-cleanup.sql"
```

**Pass looks like:** `sqlcmd` exits with no error text. Confirm with:

```powershell
(Invoke-RestMethod -Uri "http://127.0.0.1:8000/api/setup/sql/preflight" -Method Post -ContentType "application/json" -Body (@{
    host = $SqlHost; instance = $SqlInstance; database = $Database; login_name = "bbs_connector_test"
} | ConvertTo-Json)).existing_login_present
```

**Pass looks like:** outputs `False`.

### 2.5 Restore BBS's real configuration (do not skip this)

```powershell
$restorePlan = Invoke-RestMethod -Uri "http://127.0.0.1:8000/api/setup/sql/plan" -Method Post -ContentType "application/json" -Body (@{
    host = $SqlHost; instance = $SqlInstance; database = $Database
} | ConvertTo-Json)
$restorePlan.kind
$restoreApply = Invoke-RestMethod -Uri "http://127.0.0.1:8000/api/setup/sql/apply" -Method Post -ContentType "application/json" -Body (@{
    plan_id = $restorePlan.plan_id; host = $SqlHost; instance = $SqlInstance; database = $Database
} | ConvertTo-Json)
$restoreApply.verified
(Invoke-RestMethod http://127.0.0.1:8000/api/configuration).sql_user
```

**Pass looks like:** `$restorePlan.kind` is `reset_password` (confirms
this ran against the real, already-existing `bbs_connector`, not a
fresh create), `$restoreApply.verified` is `True`, and the final line
outputs `bbs_connector`.

If step 2.1 needed the offline branch, `/setup/sql/apply` won't work
here either -- use `/setup/sql/generate` with `reset_password: $true`
(no `login_name`, so it defaults to `bbs_connector`), run the resulting
SQL via `sqlcmd`, then `/setup/sql/verify-and-store` with the password
from that script, the same shape as 2.1-offline/2.2 above.

## 4. Forced driver-missing, on the installed Windows service

This sets an environment variable for the **service process**, not a
shell. Setting `$env:BBS_SETUP_FORCE_ODBC_MISSING` in a PowerShell
window does nothing to the service -- it's a separate process that
doesn't inherit your shell's environment. **Run everything in this
section as Administrator** (editing a file under Program Files and
restarting a service both require it).

### 4.1 Turn it on

```powershell
$svcXml = "C:\Program Files\BMX Broadcast Suite\BBSService.xml"
[xml]$xml = Get-Content $svcXml
$existing = $xml.service.env | Where-Object { $_.name -eq "BBS_SETUP_FORCE_ODBC_MISSING" }
if ($existing) { $existing.value = "1" } else {
    $node = $xml.CreateElement("env")
    $node.SetAttribute("name", "BBS_SETUP_FORCE_ODBC_MISSING")
    $node.SetAttribute("value", "1")
    $xml.service.AppendChild($node) | Out-Null
}
$xml.Save($svcXml)
Restart-Service BMXBroadcastSuite
```

WinSW re-reads `BBSService.xml` on every service start/restart
(`autoRefresh` defaults to `true`), so `Restart-Service` alone is
enough -- no reboot, no MSI repair.

Confirm:

```powershell
Invoke-RestMethod http://127.0.0.1:8000/api/setup/status | Select-Object -ExpandProperty odbc_driver
```

**Pass looks like:** `present` is `False`, but `installed_drivers` still
lists your real driver (e.g. `ODBC Driver 18 for SQL Server`) --
confirming the forced-missing state is showing, not a real absence.
Opening `/setup` in a browser should show the driver as **NOT FOUND**
with the license checkbox and install buttons visible.

### 4.2 Turn it off

```powershell
$svcXml = "C:\Program Files\BMX Broadcast Suite\BBSService.xml"
[xml]$xml = Get-Content $svcXml
$existing = $xml.service.env | Where-Object { $_.name -eq "BBS_SETUP_FORCE_ODBC_MISSING" }
if ($existing) { $xml.service.RemoveChild($existing) | Out-Null; $xml.Save($svcXml) }
Restart-Service BMXBroadcastSuite
```

**Pass looks like:**

```powershell
(Invoke-RestMethod http://127.0.0.1:8000/api/setup/status).odbc_driver.present
```

outputs `True` again.

## 5. Injection spot-check

```powershell
try {
    Invoke-RestMethod -Uri "http://127.0.0.1:8000/api/setup/sql/generate" -Method Post -ContentType "application/json" -Body (@{
        database = "RACE"; login_name = "bbs_connector]; DROP LOGIN [sa"
    } | ConvertTo-Json)
} catch {
    $_.ErrorDetails.Message
}
```

This endpoint never opens a SQL connection, so it's safe to run against
any SQL Server, including production.

**Pass looks like:** the `try` block throws (no SQL text is returned),
and the caught message reads:

```
'bbs_connector]; DROP LOGIN [sa' is not a usable login name -- use only letters, digits, and underscores, starting with a letter or underscore (up to 128 characters).
```

A **fail** would be either no error (a 200 with `sql` in the response),
or an error that isn't this exact plain-language rejection.

## 6. Loopback spot-check

Whether hitting your own LAN IP is enough depends on what BBS is
currently bound to. Check first:

```powershell
(Invoke-RestMethod http://127.0.0.1:8000/api/configuration).app_host
```

- **If this prints `127.0.0.1`** (the default): BBS's listening socket
  only accepts connections that arrive via loopback in the first place.
  Your LAN IP won't even be reachable on port 8000 from this machine or
  any other -- there is nothing to spot-check via the LAN IP; the
  connection itself will fail before the loopback-vs-not logic ever
  runs. Use your phone on the same Wi-Fi instead (below).
- **If this prints `0.0.0.0` or a specific LAN IP**: continue below --
  hitting your own LAN IP from this same machine is sufficient. Windows
  does not rewrite a connection to your own LAN-assigned address into
  `127.0.0.1`; the server sees the real LAN IP as the client, which
  `is_local_client()` correctly treats as non-loopback. No second device
  needed.

Find your LAN IP:

```powershell
Get-NetIPAddress -AddressFamily IPv4 | Where-Object { $_.InterfaceAlias -notmatch 'Loopback' -and $_.IPAddress -notlike '169.254.*' } | Select-Object InterfaceAlias, IPAddress
```

Then, using one of those addresses:

```powershell
$LanIp = "PASTE-THE-IP-HERE"
try {
    $resp = Invoke-WebRequest -Uri "http://${LanIp}:8000/api/setup/status" -UseBasicParsing -TimeoutSec 5
    Write-Host "FAIL: got HTTP $($resp.StatusCode) from a non-loopback address -- should have been refused" -ForegroundColor Red
} catch {
    $webResp = $_.Exception.Response
    if ($webResp -and [int]$webResp.StatusCode -eq 403) {
        Write-Host "PASS: refused with 403, as expected" -ForegroundColor Green
    } elseif ($webResp) {
        Write-Host "Unexpected status: $([int]$webResp.StatusCode)" -ForegroundColor Yellow
    } else {
        Write-Host "Could not connect at all -- check app_host above; this address likely isn't reachable. Use a phone on the same Wi-Fi instead." -ForegroundColor Yellow
    }
}
```

**Pass looks like:** `PASS: refused with 403, as expected`, printed in
green. A `FAIL` line, or any 200 response, means the setup wizard was
reachable from a non-loopback address -- stop and do not publish.

If you fall into the "use your phone" case: open
`http://<this machine's LAN IP>:8000/api/setup/status` in the phone's
browser. **Pass** is a plain `{"detail":"..."}` 403 error page, not the
JSON status object.
